# Phase 10.1: Security Audit Rule Catalog & Static Audit Engine — Research

**Researched:** 2026-09-14
**Domain:** Extending an existing, in-repo static rule-engine pattern with a new, independently-versioned
audit catalog. No external library research was needed — the entire domain this phase needs is already
implemented and precedented in this codebase.
**Confidence:** HIGH — grounded in reading the actual existing implementation, not external sources.

## User Constraints

No CONTEXT.md exists for this phase (no `/gsd-discuss-phase` was run first). Constraints instead come
directly from the user's original instruction and from `docs/SECURITY_AUDIT.md` (written this same
pass): the rule catalog must be independent of the existing risk score (not a second scoring pipeline),
must require no new credential or network access, and must produce individually identifiable,
verifiable rules.

## Existing pattern this phase extends

`core/risk` (a pure-JVM Gradle module, `kotlin("jvm")` plugin, `jvmToolchain(17)`,
dependency only on `core:model`) already implements a deterministic, unit-testable rule-engine pattern:

- `ApkAnalysisInput` (`core:model`) — a pure-Kotlin, Android-framework-free snapshot of declared/
  structural APK facts (package name, versions, min/target SDK, requested permissions, debuggable,
  native ABIs, component counts, signature-verified flag). This is the entire input surface available
  to a static rule without pulling Android dependencies into a JVM-only test target.
- `RiskRule` interface — `fun evaluate(input: ApkAnalysisInput): RiskFinding?`, returns `null` when the
  rule's condition is not met (an *additive*-score design: a non-firing rule contributes nothing).
- `RuleIds` object — every rule ID in one place, single source of truth for "what can this engine
  version produce."
- `CombinationRules.kt` — rules that require two permissions to co-occur (e.g.
  `AccessibilityOverlayCombinationRule`), each independently tested for "fires when both present, does
  not fire with only one side."
- `TestFixtures.kt` (`internal fun testInput(...)`) — a shared, override-only-what-you-need builder for
  `ApkAnalysisInput` test fixtures, used by every existing rule test.
- `RISK_ENGINE_VERSION = "static-v1"` — a version constant bumped whenever the rule set changes,
  documented in `docs/RISK_SCORING.md`'s own rule table.

## Why a pass/fail/warn catalog, not another additive score

`docs/SECURITY_AUDIT.md` (written this pass, before this research file) already settled this: Security
Audit needs individually citable, trackable checks with stable verdicts, not a second number competing
with the existing risk score for the user's attention. An additive score answers "how risky, overall?";
an audit catalog answers "did this specific, named check pass?" — a different, complementary question.
This rules out reusing `RiskRule` directly (it has no non-firing-is-still-a-reportable-outcome concept)
and motivates the new `AuditRule`/`AuditFinding`/`AuditStatus` types.

## Architectural decision: new package in `core:risk`, not a new Gradle module

Considered and rejected: a new `core:securityaudit` Gradle module. Rejected because:
- `core:risk` already has exactly the property this phase needs (pure JVM, no Android dependency, fast
  unit tests) — a new module would duplicate that setup for no isolation benefit this phase needs.
- The audit catalog's only dependency is `ApkAnalysisInput`, already `core:risk`'s existing dependency.
- A new package (`com.nadeem.apkscope.core.risk.audit`) inside the existing module gives clean separation
  (distinct types, distinct rule-ID namespace, distinct version constant) without the build-graph
  overhead of a new module, and without touching `settings.gradle.kts`.

Reused directly (via Kotlin `internal` visibility, same module): `Permissions` (permission-string
constants) and `containsAny` (list-membership helper) from `com.nadeem.apkscope.core.risk`, and `testInput(...)`
from the test source set. No duplication of these across packages.

## Rule selection for the v1 catalog

Every v1 rule had to be derivable from `ApkAnalysisInput`'s existing fields — no new static extraction
was authorized for this phase (see `docs/SECURITY_AUDIT.md`'s scope statement: "no new static extraction
is introduced by this milestone unless a specific audit rule requires a field the analyzer does not yet
expose"). Two candidate checks (`usesCleartextTraffic`, `allowBackup`) required a field that does not
exist yet — these were **not** implemented with a workaround/proxy signal; instead they were written up
honestly as a follow-up (MS10-STATIC04, `docs/SECURITY_AUDIT_RULES.md`'s follow-up note) rather than
faked. The 8 rules that were implementable from existing fields were cross-checked against a real
finding already observed in this session's own manual testing: the "Accessibility and overlay
capabilities declared together" finding shown in a real Final Report for the Risk Signal Fixture app
(screenshot reviewed earlier this session) — `AUDIT_ACCESSIBILITY_OVERLAY_TAPJACKING` is grounded
directly in that observed, real finding, not a hypothetical.

## Risks / open questions for later phases

- `AUDIT_EXPORTED_SURFACE_RATIO`'s "majority exported" threshold (`exported * 2 > total`) is this
  catalog's own choice, not derived from any external standard — flagged in
  `docs/SECURITY_AUDIT_RULES.md` as this rule's own rationale, not presented as an industry-standard
  cutoff.
- No automated guard exists yet preventing a future rule ID from colliding with `core:risk`'s existing
  `RuleIds` — currently prevented only by inspection (MS10-STATIC02, tracked as source-implemented, not
  test-covered).
- Phase 10.2's guided-session correlation rules (`AUDIT_CORR_*`) will need a way to represent "no
  session has run yet" — the `NOT_APPLICABLE` status exists in `AuditStatus` for exactly this, but no
  rule uses it yet; Phase 10.2 should verify the enum value works end-to-end before assuming it does.
