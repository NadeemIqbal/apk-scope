# External Integrations

**Analysis Date:** 2026-09-10

## Android System Services

**DevicePolicyManager (`android.app.admin.DevicePolicyManager`):**
- Purpose: Administers Managed Work Profile (`ProfileOwner`), sets restrictions, and ingests OS-level network activity events.
- Telemetry: Ingests `DnsEvent` and `ConnectEvent` via `DeviceAdminReceiver.onNetworkLogsAvailable`.

**VpnService (`android.net.VpnService`):**
- Purpose: Virtual network interface intercepting all traffic generated by apps running in the Work Profile.
- Scope: Work profile user only. **Correction, 2026-09-12 reconciliation**: `SandboxVpnService`'s
  `Builder()` call does not currently call `addAllowedApplication`/`addDisallowedApplication` — this
  line previously described intended/assumed behavior, not verified source. Confirmed via
  `dumpsys connectivity vpn` that the active VPN's `Uids` range spans the entire Work Profile user
  (e.g. `1300000-1399999`), not just the target package. See `.planning/ROADMAP.md` Phase 9.1 and
  `.planning/STATE.md`'s 2026-09-12 reconciliation section.
- **Correction 2, 2026-09-12 (post-reconciliation attempt)**: `addAllowedApplication(targetPackage)`
  was subsequently implemented and tested on a physical Pixel 8 to close the gap above, and the
  attempt is now itself architecture evidence, not a pending task. Combined with this product's
  `DevicePolicyManager.setAlwaysOnVpnPackage(lockdownEnabled = true)` policy on the same Managed Work
  Profile, the scoped `establish()` call reported success (non-null tun, no exception) but
  `dumpsys connectivity vpn` showed the resulting `Uids` as **empty** (`<{}>`) — not scoped to the
  target and not left at the whole-profile range — and the target package's own DNS resolution then
  failed completely (`UnknownHostException`, reproduced across two hosts, non-transient). The
  implementation was reverted; the whole-Work-Profile-capture behavior described above is the current,
  reinstated, verified-working state again. Three ranked, unconfirmed hypotheses for why this specific
  combination (`addAllowedApplication` + Managed Work Profile + always-on lockdown VPN) produces an
  empty enforced UID set, and the on-device test that would distinguish each, are recorded in
  `.planning/STATE.md`'s "Phase 9.1 attempt — 2026-09-12" section. Do not re-read the original
  correction above as "still just needs `addAllowedApplication` added" — that specific fix has been
  tried and disproven for this architecture; `.planning/ROADMAP.md`'s Phase 9.1 is reframed as a
  root-cause investigation, not a re-run of the same implementation.

**PackageInstaller (`android.content.pm.PackageInstaller`):**
- Purpose: Programmatically installs target APKs into the isolated Work Profile user space without prompt loops.

**Android KeyStore / Certificate Management:**
- Purpose: Secure generation and storage of local root CA keys for the experimental HTTPS inspection POC.

## Data Storage

**Databases:**
- AndroidX Room (SQLite)
  - Location: Local app data directory (`/data/user/0/com.nadeem.apkscope/databases/`)
  - Schema: Sessions, targets, declared capabilities, observed behaviors, OS evidence, risk evaluations.

**File Storage:**
- Local filesystem only (`context.filesDir`, `context.cacheDir`).
- Temporary APK staging and exported analysis reports (JSON, Markdown).

## Monitoring & Telemetry

- **Remote Telemetry:** None. All data is strictly processed on-device. Zero third-party analytics or crash reporting SDKs are integrated to preserve analyst privacy.

## CI/CD & Deployment

- Local Gradle builds via `./gradlew`.
- Testing target: Connected Android devices and emulators running API 30+.
