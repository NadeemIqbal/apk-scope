# Phase 10.2, Plan 01: Static Security Audit — First Complete User Workflow

**Goal:** A real, on-device, end-to-end workflow — select APK, run static audit, view findings/coverage,
open finding evidence/remediation, persist, restart the app, reopen the same audit.

## Architecture discovery (done before writing code)

Dispatched a read-only exploration subagent to map: type-safe Navigation Compose routes
(`Routes.kt`/`AppNavHost.kt`), the `sessionViewModel { ... }` ViewModel-per-screen convention,
`StaticResultScreen`/`StaticResultViewModel`'s existing pattern, `StaticAnalysisResultStore`'s actual
persistence mechanics (confirmed: a Java-serialization envelope carrying only 4 unrelated fields — NOT
suitable for carrying `usesCleartextTraffic`/`allowBackup` back out, despite an initial assumption it
might be), the stable `sessionId` UUID key, and the `FinalReportEntity`/`FinalReportFindingEntity` Room
precedent for a one-parent/many-children child record. This closed several wrong assumptions before any
code was written — see `.planning/STATE.md`'s Phase 10.2 checkpoint for the full report.

## Must-haves (observable truths this plan must leave TRUE)

1. A "Run Security Audit" action is reachable from Analysis Detail with no install/Work-Profile step.
2. Findings render with outcome/severity/confidence and a coverage summary matching the real analyzed APK.
3. Opening a finding shows its evidence and remediation.
4. The audit survives a real app restart (`am force-stop` + relaunch) and reopens with identical results,
   read from Room, not re-run.
5. Loading/empty/running/cancelled/error states are each implemented and distinct.
6. Security Audit never mutates the existing `StaticRiskAssessment`/risk score.
7. Zero regressions in the full JVM/Robolectric suite.

## Tasks

1. Add `ApkMetadata.allowBackup` (`core:staticanalysis`), computed in `ApkAnalyzer.kt` from
   `ApplicationInfo.FLAG_ALLOW_BACKUP`, mirroring the existing `usesCleartextTraffic` pattern.
2. Add `SecurityAuditEntity`/`SecurityAuditFindingEntity`/`SecurityAuditDao` (`core:database`), mirroring
   `FinalReportEntities.kt`. Add both new columns to `AnalysisSessionEntity` (defaulted, non-breaking).
   Bump `SandboxDatabase` version 8→9 (destructive migration, already-accepted pre-release policy).
3. Thread the two new fields through `PersistedAnalysis`/`buildPersistedRows`/`toDomain` (app domain).
4. Add `PersistedAnalysis.toRiskInput()` in `RiskInputMapper.kt` — the missing mapping needed to
   re-run an audit against an already-persisted analysis (the existing mapper only covered a fresh,
   not-yet-persisted `ApkAnalysisResult`).
5. Add `SecurityAuditRepository` (run-and-persist, observe, get), mirroring `SessionRepository`'s split.
6. Correct the audit model: `AuditOutcome` (6-value) + separate `Severity`/`Confidence`, replacing the
   Phase 10.1 draft's single `AuditStatus`. Add `AuditFinding.remediation`. Add 2 rules
   (`AUDIT_CLEARTEXT_TRAFFIC_ENABLED`, `AUDIT_BACKUP_ENABLED`) — catalog is now 10 rules.
7. Add `SecurityAuditViewModel` (5-phase state machine), `SecurityAuditScreen`,
   `SecurityAuditFindingDetailScreen`, two new routes, `AppNavHost.kt` wiring, and a "Security Audit"
   trigger row on `StaticResultScreen`.
8. Build the debug APK, install on `emulator-5554`, and perform the full real device walkthrough listed
   in `.planning/STATE.md`'s Phase 10.2 checkpoint (push a real fixture APK, select via the system
   document picker, run, inspect a finding, force-stop, relaunch, reopen, compare).
9. Re-run the full JVM/Robolectric suite; confirm zero regressions.

## Explicit non-goals for this plan

- No automated instrumentation test for the `RUNNING`/`CANCELLED` state race (MS10-UI05 partial).
- No duplication of hash/package/version/signing onto `SecurityAuditEntity` itself (MS10-FOUND01 partial
  — binds via `analysisId` reference instead).
- No secret scanning, network trust indicators, code patterns, or guided sessions (Phases 10.3+).
